# Gatekeeper V7.1 — Ranking Accuracy Patch

Root causes, confirmed from Harry's Clarke Quay field test (13 Jul 2026):

| Symptom | Root cause |
|---|---|
| 3.5★ cocktail bar ranked #1 at 60 m | Results sort by distance, not quality |
| Swee Lee "Base +150%" | Auto-appended "specialty coffee" query counted in `matched` but not in `totalWeight` — base can exceed 1.0 |
| Tiramisu shop = 100% MATCH | Query membership (weak signal) can contribute 100%+; review evidence (strong signal) capped at 40% |
| Bar shows "☕ Coffee Focus" badge | Badge is `!foodHeavy`, and `bar`/`night_club` aren't in the food list |
| Zero coffee mentions in 5 reviews → no penalty | No coffee-mention signal exists |

All changes in `src/services/livesearch.ts` + `src/modules/radar.tsx`. Est. ~100 lines.

---

## Fix 1 — Two-tier ranking: verified first, then score, then distance

Replace the final sort in `liveAreaSearch`:

```ts
// BEFORE:
filtered.sort((a, b) => (originLat !== null ? a.distanceM - b.distanceM : b.score - a.score));

// AFTER — evidence tier ▸ score ▸ distance:
filtered.sort((a, b) => {
  const tierA = a.filterEvidence ? 0 : 1;
  const tierB = b.filterEvidence ? 0 : 1;
  if (tierA !== tierB) return tierA - tierB;      // verified places always above unverified
  if (b.score !== a.score) return b.score - a.score;
  return a.distanceM - b.distanceM;               // distance = tiebreaker only
});
```

With this alone, Pour.traits (verified, 126) and Apartment (verified, 90) jump above
every "No Review Evidence" place regardless of distance. This is 70% of the fix.

Optional UI polish in `radar.tsx`: render a divider between tiers —
`"— Unverified (no review evidence) —"` — so the boundary is explicit.

## Fix 2 — Base >100% bug

`matched` can contain the auto-appended `specialty coffee` query but `totalWeight`
counts only user keywords. Two-line fix — divide by the real query count:

```ts
// where queries[] is built (after the specialty-coffee push):
const totalWeight = queries.length || 1;    // was: kws.length || 1
```

And add the regression test (tests/livesearch.test.ts):

```ts
it('base never exceeds 1.0 even when matched includes the auto-appended query', () => {
  const place = scorePlace(rawCafe, ['pour over', 'filter', 'specialty coffee'],
    { ...baseOpts, totalWeight: 3 });
  expect(place!.scoreBreakdown.base).toBeLessThanOrEqual(1.0);
});
```

## Fix 3 — Rebalance: evidence must dominate, query membership must not

In `scorePlace`, change the composition:

```ts
const base = Math.min(1, matched.length / opts.totalWeight) * 0.25;  // was full weight; now max +0.25
// evidenceScore cap: raise 0.40 → 0.50 (first hit 0.25, subsequent 0.10)
```

New weight table (document in the debug drawer labels):

| Signal | Range | Rationale |
|---|---|---|
| Review/archive evidence | 0 … +0.50 | The only trustworthy positive signal |
| Query membership (base) | 0 … +0.25 | Google relevance ≈ noise; demoted |
| Coffee-mention ratio (Fix 4) | −0.25 … +0.15 | Cheap, powerful |
| Type score | −0.25 … +0.10 | See Fix 5 |
| Rating/volume | −0.10 … +0.10 | Add a floor penalty (Fix 6) |

## Fix 4 — Coffee-mention ratio (the Kopi & Spells killer)

Five reviews, zero coffee words → almost certainly not a coffee destination:

```ts
const COFFEE_WORDS = /\b(coffee|espresso|latte|flat white|barista|brew|beans?|roast|cappuccino|long black|americano|mocha|cuppa|kopi)\b/i;

function coffeeMentionScore(reviews: string[]): number {
  if (reviews.length === 0) return 0;                      // no data — neutral
  const hits = reviews.filter(r => COFFEE_WORDS.test(r)).length;
  const ratio = hits / reviews.length;
  if (ratio === 0)   return -0.25;   // 0/5 mention coffee → bar/dessert/etc.
  if (ratio < 0.4)   return -0.10;   // 1/5 — coffee is incidental
  if (ratio >= 0.8)  return +0.15;   // 4-5/5 — reviewers come FOR the coffee
  return +0.05;
}
```

Add `coffeeMention` to `ScoreBreakdown` and show it in the debug drawer
("Coffee-Mention Ratio: 0/5 reviews → −25%"). Field-test expectations:
Kopi & Spells 0/5 → −0.25; Swee Lee ~4/5 → +0.15 but demoted by Fixes 2+3;
Pour.traits 5/5 → +0.15.

Test: reviews `['great cocktails','fun band','nice pizza']` → penalty −0.25;
reviews `['best filter coffee','barista knows beans']` → +0.15.

## Fix 5 — Nightlife/dessert type penalty + honest badges

```ts
const NIGHTLIFE = ['bar', 'night_club', 'pub', 'wine_bar', 'liquor_store'];
const DESSERT   = ['dessert_shop', 'ice_cream_shop', 'bakery', 'cake_shop', 'chocolate_shop'];

const allTypes = [raw.primaryType, ...(raw.types ?? [])].filter(Boolean) as string[];
let typeScore = 0;
if (allTypes.some(t => NIGHTLIFE.includes(t)))      typeScore = -0.25;
else if (foodHeavy || allTypes.some(t => DESSERT.includes(t))) typeScore = -0.15;
else if (strictCoffee)                              typeScore = 0.10;
```

Badge logic in `radar.tsx` — stop implying coffee focus by default:
- `☕ Coffee Focus` only when `primaryType` is `coffee_shop`/`coffee_roastery`
- `🍸 Nightlife` when nightlife types present
- `🍔 Food Heavy` as today
- otherwise no type badge at all

## Honest limits (so expectations stay calibrated)

- Google returns only ~5 review snippets per place. If a gem's pour-over evidence
  isn't in those 5, it lands in tier 2 with a clean score — the tier divider in the
  UI says "no evidence", not "bad café". This is an API ceiling, not a code flaw.
- `websiteUri` is already in the FIELD_MASK: a future v8 could fetch the café's own
  site/menu and scan it for brew methods — much richer evidence than 5 snippets.
  (Needs a CORS proxy or serverless function; note it as a v8 candidate, not v7.1.)
